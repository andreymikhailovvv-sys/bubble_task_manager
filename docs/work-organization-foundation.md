# Планировыч Work · Корпоративное ядро, этап 1

Новый организационный слой **над** существующим личным Планировычем. Никаких изменений Task/Sphere, пользовательских заметок, чатов, календаря, AI-биллинга или Telegram интеграций.

## PR 1: физическая организация и членство

- Organization: серверный владелец будущих корпоративных проектов и данных; идентификатор, имя и даты.
- OrganizationMember: одна запись на пользователя в организации, роли OWNER/ADMIN/MANAGER/MEMBER/VIEWER; уникальная пара organizationId/userId.
- Пользователь может состоять в нескольких организациях.
- При создании организации роль OWNER присваивается **атомарно**, в одной транзакции nested-create.
- По текущему пилотному режиму создавать компании разрешается только существующему зарегистрированному пользователю, чей ID внесён в BUSINESS_ADMIN_USER_IDS.
- Списки и карточки организаций доступны только их действующим участникам; запрос по чужому ID возвращает 404.
- Work показывает реальные компании и позволяет создать первую. Пустой список отображается честно, без фиктивной статистики.
- Никаких приглашений, изменения ролей, удаления участников/организаций или полноценного Company Workspace UI в этом PR.

## API

- GET /api/business/organizations — только организации текущего аутентифицированного пользователя.
- POST /api/business/organizations — создание компании администратором Work: { "name": "Компания Альфа" }.
- GET /api/business/organizations/:organizationId — возвращает карточку только участнику.

Используется текущая host-only авторизация, без открытия прав на личные данные. Корпоративные маршруты доступны с JWT только в рамках членства; CORS и доступ в BusinessApp остаются прежними.

## Обновление базы данных и безопасность релиза

Это **реальная, но исключительно добавляющая** миграция PostgreSQL. При запуске Timeweb выполнить стандартный Prisma migrate deploy через существующий механизм сервера. Рекомендуется обычная резервная копия БД перед первым релизом с организационными таблицами. Роллбек кода не удаляет таблицы и данные. Отдельную rollback-миграцию с удалением таблиц на продакшене делать нельзя.

Существующие личные задачи по-прежнему принадлежат User. Не подставлять organizationId в старые API до полного tenant-aware RBAC. При удалении единственного OWNER через существующую функцию удаления личного аккаунта может остаться организация без участников; до коммерческого доступа потребуются политика удаления организации/передачи владения и очистка пустых организаций.
