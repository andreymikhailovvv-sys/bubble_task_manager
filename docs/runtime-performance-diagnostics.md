# Диагностика производительности Планировыча

Назначение: выяснить причины роста CPU и задержек при малом числе пользователей. Добавлена **только телеметрия**, без изменения логики задач, мониторинга, почты, Telegram или AI.

## После объединения PR и деплоя

Ничего дополнительно включать не требуется. По умолчанию диагностика активна. В логах Timeweb фильтруйте:

- `[PerfDiag] enabled` — запуск и параметры измерений;
- `[PerfDiag] snapshot` — один агрегированный снимок каждые 30 секунд.

Сопоставляйте поле `at` (UTC, ISO 8601) со временем на графике Timeweb **с учётом часового пояса графика**. Для московского времени 09:52 это 06:52 UTC.

Поля снимка:
- `cpuOneCorePct`: процессорное время процесса Node.js как процент **одного ядра** за окно. Значение может быть больше 100 на многопроцессорном хосте; это не равно проценту CPU виртуальной машины в Timeweb.
- `rssMb`, `heapUsedMb`, `heapTotalMb`: память процесса.
- `eventLoopUtilPct`, `eventLoopDelayP95Ms`, `eventLoopDelayMaxMs`: занятость и задержки цикла событий Node.js. Высокая задержка при высоком CPU часто указывает на блокирующую работу в приложении.
- `httpCount`, `httpTop`: число HTTP-запросов, наиболее дорогие группы маршрутов, количество ошибок 5xx / обрывов, среднее, максимум и верхняя граница p95.
- `workerTop`: время выполнения фоновых циклов по именам; `totalWallMs` суммирует длительность вызовов и может включать параллельные ожидания, **это не CPU-потребление**.
- `dbQueryCount`, `databaseTop`: число SQL-запросов и наиболее тяжёлые группы вида `SELECT:Task` / `UPDATE:Task`. SQL-текст и параметры не сохраняются. Длительность события Prisma относится к SQL-выполнению и не заменяет замер времени пользовательского сценария, пула соединений или сети.

Для HTTP `p95LeMs` означает **верхнюю границу фиксированного интервала**, а не точный p95. Поля `slow` отражают превышения соответствующего порога. Данные относятся только к текущему окну и обнуляются после записи в лог. Несколько реплик имеют отдельные `pid` и снимки.

### Как разбирать новый пик

1. Найдите `[PerfDiag] snapshot` с `at` в интервале ±2 минуты от пика CPU в Timeweb.
2. Посмотрите, высок ли `cpuOneCorePct` и `eventLoopDelayMaxMs`. Если CPU Timeweb высок, а CPU Node.js низок, проверьте другие процессы/контейнеры или саму VM.
3. Проверьте `workerTop` и `databaseTop`. Высокий `totalWallMs` у worker без задержки event loop может означать ожидание API/сети, а не вычислительную перегрузку.
4. Проверьте `httpCount`. При 1–3 пользователях большой `httpCount` может указывать на polling клиентского приложения, ретраи или внутренние запросы, а не на множество людей.
5. Для расследования SQL-интенсивности анализируйте `dbQueryCount` и максимальные длительности по таблицам. Не включайте сырые Prisma query logs ради диагностики.

### Переменные сервера

- `PERF_DIAGNOSTICS_ENABLED=false` — полностью отключить диагностику (опционально после исследования).
- `PERF_DIAGNOSTICS_WINDOW_MS=30000` — окно 15 000–300 000 мс, по умолчанию 30 000.
- `PERF_DIAGNOSTICS_SLOW_HTTP_MS=2000` — порог медленного HTTP-запроса.
- `PERF_DIAGNOSTICS_SLOW_DB_MS=250` — порог медленного SQL-запроса.

Не требуется токен, ручное открытие панели администратора или внешний сервис. В логах нет содержимого HTTP, SQL и параметров, тел Telegram, задач, email-адресов и ID пользователей.

**Ограничения:** встроенная диагностика не даёт CPU-профиль по отдельным JS-функциям. Для однозначного определения горячей функции после сбора метрик потребуется CPU-профиль/флеймграф. Первым этапом мы определяем, связан ли пик с Node.js, БД, сетью, HTTP либо фоновой активностью.
