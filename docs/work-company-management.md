# Планировыч.Бизнес: кабинет компании · этап 2

Продолжение организационного ядра, созданного в PR #1200. Новый бизнес-кабинет `/organizations/:id` открывается из списка компаний на Work. В нём работают: обзор, команда, подразделения, одноразовые ссылки-приглашения и настройки названия компании.

## Пользовательские сценарии

1. Войти на `work.planirovych.ru` под разрешённым аккаунтом, открыть организацию щелчком в списке.
2. В разделе «Команда» владелец/администратор создаёт подразделения, переименовывает их, распределяет участников.
3. Создать приглашение на роль (ADMIN только владельцем; MANAGER/MEMBER/VIEWER владельцем и администратором), **сразу скопировать ссылку**.
4. Приглашённый с зарегистрированным аккаунтом открывает `https://work.planirovych.ru/join/<token>`, входит и принимает приглашение. Если вошёл до перехода по ссылке, нажимает «Присоединиться».
5. После вступления обычный сотрудник может войти в Work даже без `BUSINESS_ADMIN_USER_IDS`. Отображаются только организации, в которых он состоит.
6. Владелец меняет роли, может назначить второго владельца; нельзя удалить/понизить последнего владельца.
7. Кнопка «Все организации» возвращает в список; прямое открытие `/organizations/:id` работает после перезагрузки.

## API и модель данных

- Дополнительные `OrganizationDepartment` и `OrganizationInvitation`, и nullable `OrganizationMember.departmentId`.
- GET `/api/business/organizations/:id/workspace`: данные только действующему члену организации.
- PATCH `/api/business/organizations/:id`: переименование владельцем/админом.
- POST/PATCH/DELETE `/api/business/organizations/:id/departments`: управление отделами владельцем/админом.
- PATCH/DELETE `/api/business/organizations/:id/members/:memberId`: смена роли, отдела, удаление участника или выход из компании с серверной RBAC-проверкой.
- POST/DELETE `/api/business/organizations/:id/invitations`: создание/отзыв ссылок.
- GET `/api/business/invitations/:token`: публичная предварительная карточка.
- POST `/api/business/invitations/:token/accept`: вступление под зарегистрированным аккаунтом, атомарное однократное использование ссылки.

Секрет ссылки генерируется `crypto.randomBytes(32)`, в БД только SHA-256; действие доступно один раз в течение семи дней, 15 созданий/час/организацию. Ссылки в последующих API не возвращаются. Для изменения владельца и удаления сотрудника используются SERIALIZABLE транзакции. Администратор организации не может назначить владельца/админа или изменять их роли.

## Защита и ограничения

- Личный Планировыч, существующие Task/Sphere, Telegram Mini App, Android, биллинг и их авторизация не изменяются.
- Все корпоративные GET/мутирующие API проверяют действующее членство на сервере.
- Только платформа-администратор может **создавать новые организации**. Участники могут пользоваться Work.
- Приглашаются только **существующие зарегистрированные пользователи**; самостоятельная регистрация и email-рассылка отсутствуют.
- Должна быть сделана стандартная резервная копия PostgreSQL перед merge/deploy: миграция добавляет новые таблицы и необязательный столбец, не обновляя старые строки.
- При удалении личного аккаунта владельца через старый endpoint пока отсутствует глобальная защита от осиротевшей организации. Этот сценарий нужно закрыть перед коммерческим открытием.
- «Проекты» и «ИИ-диспетчер» честно показывают заглушки, но не личные данные. Реальные проекты последуют после разработки tenant-owned Project/Task.

## QA

Проверить создание и обновление отделов, приглашение, ревокацию, однократное принятие, смену ролей, невозможность удаления последнего владельца, чтение чужой организации (404), вход приглашённого без платформенного allowlist, обновление страницы на прямом пути компании, затем личный Планировыч.
